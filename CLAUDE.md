# Заметки для сессий Claude

## Совместимость версий: ветка `testing` и `main`

- **Внутри ветки `testing` совместимость между версиями не поддерживаем.** Если формат данных меняется по сравнению
  с прошлой тестовой версией — меняем его без миграций и без «переводчиков» старых форматов. Файл старого тестового
  формата просто читается как пустой и перезаписывается (так устроен `upgrade` в `src/core/schema/docType.ts`).
  Не пишите миграции, legacy-код и «перенос настроек из 0.x», если эти форматы были только в `testing`.
- **Совместимость сохраняем только с веткой `main`.** Всё, что выпущено в `main` (форматы файлов рабочей папки,
  `$type`/`$version` документов, пути файлов, id полей в `src/core/schema/fields.ts`, ключи настроек, имена древ базы,
  форматы экспорта), должно читаться новой версией — для этого пишется миграция `N → N+1` в `defineDocType`.
- **Если изменение затрагивает совместимость с `main` — обязательно предупредить пользователя** в ответе (до или
  вместе с изменением): что именно меняется, какие данные из `main` это задевает и как они будут перенесены.
  Молча ломать совместимость с `main` нельзя.
- Что сейчас в `main`, смотреть так: `git fetch origin main && git ls-tree -r --name-only origin/main`.
  Пока там только начальный коммит (README) — выпущенных форматов нет, сохранять нечего.

## Остальные договорённости

- Работаем и пушим в ветку `testing`. После каждого изменения пересобирать готовый файл `DocAssist.html`
  (`npm run build:html`) и коммитить его вместе с кодом.
- Перед пушем подтягивать `origin/testing`: в ветке работают и другие сессии. Чужие коммиты не перезаписывать —
  сливать (merge), конфликт в `DocAssist.html` решать пересборкой.
- Примеры и тестовые данные — только нейтральные («Фамилия», «01.01.2000», «000-000-000 00», «Респ. Регион»),
  никаких реальных людей.
- Тексты для работников — простые, без технических слов (Lua, regex, код). Техническое — только в разделах
  «для настройщика» и во вкладке «Справка».

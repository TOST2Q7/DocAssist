# Заметки для сессий Claude

## [ ! ] Сначала определите фокус: приложение или весь сайт

Каждое приложение на сайте — **отдельная часть системы** (отдельная «ветка» работы): своя папка `src/apps/<id>/`,
свои экраны, тексты, настройки и версия в `manifest.ts`. Сейчас это «Проверка анкет» (`anketa`), «Личные дела»
(`lichnye-dela`), «Генератор документов» (`doc-generator`: учётная карточка члена организации). Приложения разрабатываются отдельно, сами по себе.

**Но все они — части одной системы:** одно ядро, одни данные, которые приложения берут друг у друга, и общие базы.

Как работать в сессии:

1. **Определить фокус в начале.** Пользователь работает с конкретным приложением — работаем с ним: его папка, его
   экраны, его тексты. Задача про весь сайт (главная, меню, оформление, ядро, сборка, данные для всех) — работаем
   с сайтом целиком. Непонятно, о чём речь, — спросить.
2. **Не трогать другие приложения «по пути».** Если задача в одном приложении требует правки в другом — сказать
   пользователю и сделать это отдельным, явным шагом.
3. **Ядро общее для всех:** `src/core/` (рабочая папка, база людей, базы-древа, переменные, словарь подсказок, поля
   анкеты, таблицы, Lua…), `src/shared/`, `src/ui/`, стили. Меняя ядро, найти всех, кто им пользуется (grep по
   `src/apps`), проверить, что они не сломались, и сказать пользователю, какие приложения это задело.
4. **Данные общие — берём через ядро, а не из чужого приложения:**
   - общие: база людей (`.docassist/people.json`, `core/people`), базы-древа (`.docassist/base/`, `core/base`),
     глобальные переменные, словарь подсказок, общий язык полей анкеты (`core/schema/fields.ts`);
   - свои данные приложения — в его папке рабочей папки («Проверка анкет/», «Личные дела/»);
   - приложение не импортирует код другого приложения (`src/apps/другое/…`) и не читает его файлы напрямую.
     Если чем-то нужно поделиться — вынести это в ядро.
   - Формат общих данных меняется осторожно: его читают все приложения (и см. правила совместимости ниже).
5. **Новое приложение** — новая папка `src/apps/<id>/` с `manifest.ts`, реестр подхватит его сам
   (README → «Как добавить приложение»).
6. **Версии:** у приложения — своя версия в `manifest.ts` (по ней показывается «Обновлено»), у сайта — `package.json`.
7. «Ветка» здесь — часть системы, а не git-ветка: в git все приложения живут в `testing`, пока пользователь не скажет
   иначе.

## Совместимость версий: ветка `testing` и `main`

- **Внутри ветки `testing` совместимость между версиями не поддерживаем.** Если формат данных меняется по сравнению
  с прошлой тестовой версией — меняем его без миграций и без «переводчиков» старых форматов. Файл старого тестового
  формата просто читается как пустой и перезаписывается (так устроен `upgrade` в `src/core/schema/docType.ts`).
  Не пишите миграции, legacy-код и «перенос настроек из 0.x», если эти форматы были только в `testing`.
- **Совместимость сохраняем только с веткой `main`.** Всё, что выпущено в `main` (форматы файлов рабочей папки,
  `$type`/`$version` документов, пути файлов, id полей в `src/core/schema/fields.ts`, ключи настроек, имена древ базы,
  форматы экспорта), должно читаться новой версией — для этого пишется миграция `N → N+1` в `defineDocType`.
- **Если изменение затрагивает совместимость с `main` — обязательно предупредить пользователя** в ответе (до или
  вместе с изменением): что именно меняется, какие данные из `main` это задевает и как они будут перенесены.
  Молча ломать совместимость с `main` нельзя.
- Что сейчас в `main`, смотреть так: `git fetch origin main && git ls-tree -r --name-only origin/main`.
  Пока там только начальный коммит (README) — выпущенных форматов нет, сохранять нечего.

## Релизы

- **Релизы пользователь создаёт сам — скриптом `tools/da`** (`da release`, см. `tools/README.md`) на своём Mac.
  Скрипт берёт версию из `package.json` и описание из `docs/releases/vX.Y.Z.md`, проверяет и вызывает
  `gh release create`; файлы собирает `.github/workflows/release.yml`.
- Поэтому сессии **не создают релизы и теги сами**. Чтобы версия была готова к выпуску: поднять `version` в
  `package.json` (и `package-lock.json`), написать `docs/releases/vX.Y.Z.md` (формат — как у прошлых версий:
  простыми словами для работников, таблица файлов в конце), запушить в `testing` — и сказать пользователю, что можно
  выпускать через `da release`.
- Скрипты в `tools/` должны работать в bash 3.2 и с BSD-утилитами macOS: без `declare -A`, `mapfile`, `${x,,}`,
  `sed -i`, `readlink -f`. Проверка: `shellcheck -x -s bash tools/da tools/lib/*.sh`.

## Остальные договорённости

- Работаем и пушим в ветку `testing`. После каждого изменения пересобирать готовый файл `DocAssist.html`
  (`npm run build:html`) и коммитить его вместе с кодом.
- Перед пушем подтягивать `origin/testing`: в ветке работают и другие сессии. Чужие коммиты не перезаписывать —
  сливать (merge), конфликт в `DocAssist.html` решать пересборкой.
- Примеры и тестовые данные — только нейтральные («Фамилия», «01.01.2000», «000-000-000 00», «Респ. Регион»),
  никаких реальных людей.
- Тексты для работников — простые, без технических слов (Lua, regex, код). Техническое — только в разделах
  «для настройщика» и во вкладке «Справка».

## Google API (Диск, Таблицы): лимиты и обязательные проверки

Работа с Google Диском и Таблицами планируется прямо из браузера, без своего сервера. У API есть лимиты, и их нужно
учитывать при каждом изменении кода, который обращается к Google. В чувствительных местах обязательны проверки,
повторы и понятные пользователю сообщения.

### Лимиты (проверять актуальность по ссылкам ниже)

| Сервис | Лимит | Что из этого следует |
|---|---|---|
| Sheets API | 60 чтений и 60 записей в минуту на человека; **300 в минуту на всё приложение** (общие для всех пользователей) | Таблицу читать одним запросом целиком, сохранять одним пакетом (`values.batchUpdate`). Никаких запросов «на каждую ячейку» |
| Sheets API | Пакетный запрос считается за один | Группировать изменения перед отправкой |
| Drive API | ~12 000 запросов в минуту на человека; есть скрытое ограничение частоты записи | Массовую загрузку вести очередью (3–4 параллельно), а не всё разом |
| Drive API | Пакет — до 100 операций; загрузка и скачивание содержимого в пакет не входят | Проверка многих файлов — пакетами (`drive.getMany`); файлы — по одному в очереди (`runQueue`) |
| Drive API | Выгрузка Google Таблицы или Документа в файл — около 10 МБ | Для больших таблиц читать через Sheets API, а не выгрузкой |
| Google Диск | 15 ГБ на аккаунт (общие с Gmail и Фото); файл занимает место у того, кто загрузил | Предупреждать о размере, по возможности сжимать сканы |
| Токен доступа | Живёт около часа; refresh token в браузере нет | Обновлять токен в обработчике клика (окна вне клика блокируются) |

### Обязательно в коде, который ходит в Google

- **Повтор с паузой** (экспоненциальная задержка) на `429` и `403 rateLimitExceeded` / `userRateLimitExceeded`.
  Не повторять бесконечно; после нескольких попыток — сообщение пользователю.
- **Разбор ошибок, а не падение:**
  - `401` — истёк токен: получить новый и повторить, файлы заново не выбирать;
  - `403 appNotAuthorizedToFile` — человек не показывал файл приложению: предложить окно выбора (Picker);
  - `403 insufficientFilePermissions` — нет прав на Диске: сообщить, что права выдаёт админ;
  - `404` — файла нет **или** нет доступа (Google их не различает): пометить «пропал», ничего не создавать молча.
- **Перед записью в Таблицу** перечитать строки и найти нужную по ключу (ФИО / №), а не по номеру строки:
  номера сдвигаются при вставке и сортировке. Сверить, что значение не изменилось с момента чтения; если изменилось —
  показать конфликт, не затирать. Писать с `valueInputOption: RAW`, чтобы не терялись ведущие нули и даты.
- **Файлы Диска** — ключом всегда ID, не имя и не путь (имена не уникальны). Проверять `trashed`.
  Не воссоздавать удалённые файлы автоматически — спрашивать пользователя.
- **Повторная загрузка после обрыва** — через возобновляемую загрузку (resumable), чтобы не плодить копии;
  перед загрузкой сверять `md5Checksum` с уже известными файлами.
- **Токен** — только в памяти (или `sessionStorage`). Никогда не писать его в рабочую папку, резервные копии,
  «Скопировать настройки» и журналы.

### Принятые решения

- Доступ к Диску — узкий пропуск `drive.file` + Google Picker (без проверки Google и без лимита пользователей).
  Доступ у каждого человека свой: файл, показанный или созданный приложением у одного, у другого даёт
  `403 appNotAuthorizedToFile`.
- Google работает только в веб-версии / установленном PWA (адрес `https://tost2q7.github.io`, вписан в Client ID).
  Версия-файл (`IS_SINGLE_FILE` в `src/core/config.ts`) открывается с `file://` без адреса — Google в ней не работает,
  кнопки Google там нужно прятать.
- Client ID и API-ключ не секретные и могут лежать в коде (`src/core/google/config.ts`, как получить —
  `docs/GOOGLE-SETUP.md`); client secret в браузерном коде не нужен и не должен появляться.

### Блоки: каждый в своей ячейке

- **Google** — только `src/core/google` (вход, `gfetch`, Picker, Drive, Sheets). Приложения и другие блоки обращаются
  к нему через `@/core/google` и сами `fetch` к Google не делают.
- **Шифрование** — только `src/core/vault` (`lock`/`unlock`, ключ из фразы, запомнить ключ). Способ шифрования наружу
  не выносить: ни в формат файла (там только случайные на вид байты), ни в тексты интерфейса, ни в другие модули.
  Фраза нигде не хранится; восстановления нет и не делать.
- **Проверка безопасности** — `src/core/security` (+ CSP в `vite.config.ts`). Новые внешние адреса (скрипты, запросы,
  окна) добавлять в CSP и в список доверенных в `security.ts`, иначе браузер их заблокирует, а проверка покажет «чужое».
- **Метки и расхождения** — `src/core/device` (`makeStamp`, `formatStamp`, `decideSync`) и `src/ui/ConflictDialog.tsx`.
  Любая сверка «устройство ↔ Google» показывает человеку обе версии с меткой «дата, время, устройство» и спрашивает,
  какая верная и переписывать ли другую сторону. Ничего не перезаписывать молча.
- **Личные настройки на личном Диске** — `src/core/sync`. Что переносится — группы: `settingsFiles` всех приложений,
  ядро (переменные, база данных) и `syncGroups` в манифесте приложения. Личные данные людей — только группами с
  `personal: true` (по отдельному согласию). Бесспорное применяется сразу, спорное — человеку.

### Как устроено в приложениях

- «Личные дела» ↔ Google Диск — `src/apps/lichnye-dela/drive` (`Личные дела/drive.json`). Личная папка на устройстве —
  главное хранилище; Диск — выданная человеку папка со строгими правилами (имена, места, цвета папок), туда кладём только
  по правилам (`rules`). Древо папок человек ведёт сам (приложение не видит Диск целиком). Сверка — по MD5, история
  сверки (`base`) у каждого устройства своя. Миниатюры — только из файлов на устройстве.
- «Проверка анкет» ↔ Google Таблицы — `src/apps/anketa/google` (`Проверка анкет/google.json`, снимки в
  `Проверка анкет/Google Таблицы/`). Пометки (`session.notes`) — только в приложении, в таблицу не пишутся.
- Проверить Google-части без настоящего аккаунта можно на подставном Google: временно вписать тестовые ключи в
  `config.ts`, собрать (`vite build --outDir dist-test`), подменить в Playwright адреса `accounts.google.com/gsi/client`,
  `apis.google.com/js/api.js`, `www.googleapis.com/**`, `sheets.googleapis.com/**` и вернуть `config.ts` как был.
